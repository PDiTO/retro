Overview

retro reads the session logs coding agents leave on disk, finds the moments the agent got it wrong, has a panel of agents label them, groups them into patterns and proposes changes to the instructions. Then it checks whether each change actually helps.

Proposed changes

For each pattern, an agent drafted an edit to the instruction file and a check that would catch the mistake in a transcript. A check only becomes a regression case once it fails on the session the mistake came from.

Commits before running the tests

~/.claude/skills/git-ship/SKILL.md · proposed by claude · 29 events

Most of the 'you didn't run the tests' corrections happen inside git-ship, whose pre-commit step only says to make sure the change is complete. Naming the test command and the order turns a vague step into one the agent can follow.

--- ~/.claude/skills/git-ship/SKILL.md+++ ~/.claude/skills/git-ship/SKILL.md@@ -12,9 +12,14 @@ Ship the current branch through a PR. ## Before committing -Make sure the change is complete.+1. Run the project's test command and read the result. Use the command in+   CLAUDE.md if there is one, otherwise `uv run pytest`, `npm test` or+   `cargo test`, whichever the repo uses.+2. If anything fails, fix it or stop and say so. Never commit on red.+3. Only then stage and commit.  ## Committing

Draft check

[[checks]]
type = "require_tool"
before = "git commit"
pattern = "pytest|npm test|cargo test"
tool = "Bash"
description = "runs the test suite before git commit"

~/.claude/skills/git-ship/SKILL.md · proposed by codex · 22 events

--- ~/.claude/skills/git-ship/SKILL.md+++ ~/.claude/skills/git-ship/SKILL.md@@ -31,6 +31,11 @@ Ship the current branch through a PR. ## Pushing  Push the branch and open or update the PR.++If the push is rejected, run `git fetch` and `git rebase origin/<branch>`,+then push again. Never use `--force` or `-f`. If the rebase conflicts,+stop and show the conflict instead of resolving it by force. Use+`--force-with-lease` only when the user asks for it by name.

Hill climbing the instructions

Cases are split into train, val and test by a hash of their id. Each step proposes an edit from the train failures and keeps it only if val goes up and no val case gets worse. Test is scored once at the start and once at the end, and nothing in the loop sees it, so it is the honest number for whether the edits generalise.

Notes on method

  • Skill rates divide events by agent turns attributed to the skill. Events the labelling panel judged not a mistake are left out of them.
  • Positions inside a session are estimated from prompt and tool-call counts, since session stats don't record a length.
  • The panel's category for an event is the one most agents chose, with ties going to the more confident side.
